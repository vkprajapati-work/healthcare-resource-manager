How a request flows

Every request passes through the same Express pipeline first — helmet → cors → rate-limit → mongo-sanitize → hpp → body-parser → request-logger — then branches by route. Three shapes cover everything below.

Public read — GET /resources, GET /resources/:id, GET /health
Client→ validateRequest (Zod)→ controller→ service→ repository→ Mongoose / MongoDB→ DTO → envelope → 200

No auth middleware in this chain at all — matches the "find nearby, one click" requirement that reads need no login.

Admin write — PATCH / DELETE /resources (POST is currently disabled)
Client + cookie→ authenticate→ authorize(ADMIN)→ validateRequest (Zod)→ controller→ service→ repository→ Mongoose / MongoDB→ DTO → envelope → 200

authenticate verifies the JWT, loads the user, and rejects with PASSWORD_CHANGE_REQUIRED if mustChangePassword is set. authorize(ADMIN) then checks the role. Either gate failing short-circuits before Zod ever runs.

Login — POST /auth/login
Client (email + password)→ Zod validate→ AuthRepository.findByEmailWithPassword→ bcrypt.compare→ sign access + refresh JWT→ set httpOnly cookies → 200

The password hash is select: false on the schema — only this explicit lookup can see it; every other query gets the user without it.

Any failure, anywhere in the chain above
thrown AppError subclass→ asyncHandler catches→ central error middleware→ mapErrorToHttpResponse→ { success:false, error:{code,message,details?} }

Same envelope for a 400, 401, 403, 404, or 500 — the frontend only ever needs one error-handling code path.

Auth

Cookie-based JWT session. login sets httpOnly access + refresh cookies — pass -c cookies.txt -b cookies.txt in curl to carry them across requests.

POST /auth/login Public

Exchanges credentials for a session. Sets accessToken / refreshToken cookies.

Request
curl -c cookies.txt \
  -X POST http://54.235.96.72/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@healthcare.local","password":"Admin@123"}'
200 · re-verified 2026-07-12
{
  "success": true,
  "data": {
    "user": {
      "id": "6a50b173331adb584378d00a",
      "email": "admin@healthcare.local",
      "role": "ADMIN",
      "firstName": "System",
      "lastName": "Admin"
    }
  }
}

This deployment has no TLS in front of it yet, so both cookies are set with HttpOnly; SameSite=Lax and deliberately no Secure flag (COOKIE_SECURE=false) — a browser drops a Secure cookie on plain HTTP, which would silently break every authenticated request after login. Flip COOKIE_SECURE=true once this sits behind HTTPS.

POST /resources Disabled — see note

Temporarily disabled for every caller, including ADMIN. Create rich doctor/vehicle records via POST /doctors or POST /vehicles instead — both already show up in GET /resources through the read bridge above. The route, auth gate, and body validation are all still wired up underneath; a single guard (blockResourceCreation in resources.routes.ts) short-circuits every request right after the ADMIN check.

Files

Standalone upload/list/download for any of the 17 categories (2 image, 15 document). Listing and reads are scoped to the uploader unless the caller is ADMIN. Document categories are never served by the public static route — only image categories (PROFILE_IMAGE, VEHICLE_PHOTO) are.

Seed — dev-only utility, not part of the product API

Generates mock doctors, then vehicles, then drivers (in that order, so drivers can be assigned to an already-created vehicle) by calling the exact same service methods a real admin request uses — same uniqueness checks, same auto-provisioned logins, same "vehicle needs ≥1 photo" rule. Hard-blocked when NODE_ENV=production — the route 404s outright rather than just refusing auth, so it isn't reachable in a real deployment at all.

POST /seed/demo-data?count=20 Admin (dev/test only)

count is optional — defaults to 20, min 1, max 50. Creates exactly count of each type (so the default call produces 20 doctors + 20 vehicles + 20 drivers = 60 records). Names/specialties/cities are drawn from small pools and combined by index so records look distinct; every unique field (email, license number, employee ID, registration/vehicle number, phone) gets a timestamp+index suffix, so repeated calls never collide.

Every defaultPassword is a real CSPRNG-generated password, same as a real provisioning create — log in with any of them to explore the app as that doctor/driver. Profile/vehicle photos are a real uploaded file too: a 1×1 placeholder PNG embedded in the seed code itself (no fixture images shipped, no network dependency), pushed through the identical upload pipeline a multipart request would use.

One thing worth remembering

Doctors and vehicles are bridged into GET /resources read-only, but the bridge is one-directional and read-only. Creating/editing a doctor or vehicle still only happens through /doctors or /vehicles — /resources's own write endpoints never touch those collections. /drivers isn't bridged at all: a driver isn't an "ambulance or doctor." See PROJECT_CONTEXT.md §8a for the full design and its known scale limit (all three sources are fetched unpaginated and merged in application code - fine for this app's size, not meant for a large fleet).
